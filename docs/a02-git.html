A2 · Version control with Git, GitHub and GitLabA2 · Gestion de versions avec Git, GitHub et GitLab

~3.5 h

By the end of this session you will be able to

  • explain what Git does (a history of your project) and what GitHub / GitLab add (a shared copy online);
  • configure Git, and commit changes from RStudio or the terminal;
  • read the history, compare versions and go back to an old version of a file;
  • write a good .gitignore for an R project (and keep personal or large data out);
  • connect a project to GitHub or GitLab (HTTPS token or SSH key, several accounts), push and pull;
  • use a branch, and solve a simple merge conflict.

À la fin de cette séance vous saurez

  • expliquer ce que fait Git (un historique de votre projet) et ce qu’ajoutent GitHub / GitLab (une copie partagée en ligne) ;
  • configurer Git, et valider (commit) des modifications depuis RStudio ou le terminal ;
  • lire l’historique, comparer des versions et revenir à une ancienne version d’un fichier ;
  • écrire un bon .gitignore pour un projet R (et garder hors du dépôt les données personnelles ou volumineuses) ;
  • relier un projet à GitHub ou GitLab (jeton HTTPS ou clé SSH, plusieurs comptes), pousser (push) et récupérer (pull) ;
  • utiliser une branche, et résoudre un conflit de fusion simple.

Data of this session (simulated). reef_project_git.zip contains the reef-monitoring project of the NGO with its Git history: six commits made in May 2025 by the two analysts, Fara and Hery, while they prepared the coral analysis (import, cleaning, a bleaching indicator whose threshold was changed after a meeting with the MPA managers, figures). Type: an R project + the hidden .git/ folder that stores every version. The commands below are run on a copy made for this page.

Git in one pictureGit en une image

Without Git, versions live in file names (analysis_v3_FINAL.R) and nobody knows what changed. With Git, the folder contains one version of each file, and a hidden .git/ folder keeps every saved state (a commit) with its date, author and a message explaining why.

Word Meaning
repository (repo) a project folder followed by Git (it contains .git/)
commit a saved snapshot of the project, with a message; identified by a code (hash), e.g. 4a5c8d0
staging (git add) choosing which changes go into the next commit
remote a copy of the repository on a server: GitHub, GitLab (or Bitbucket)
push / pull send your commits to the remote / get the commits of others
clone download a whole repository (with its history)
branch a parallel line of work, merged back later

Sans Git, les versions vivent dans les noms de fichiers (analyse_v3_FINAL.R) et personne ne sait ce qui a changé. Avec Git, le dossier contient une seule version de chaque fichier, et un dossier caché .git/ garde chaque état enregistré (un commit) avec sa date, son auteur et un message expliquant pourquoi.

Mot Signification
dépôt (repository, repo) un dossier de projet suivi par Git (il contient .git/)
commit un instantané enregistré du projet, avec un message ; identifié par un code (hash), ex. 4a5c8d0
indexation (git add, staging) choisir quelles modifications vont dans le prochain commit
dépôt distant (remote) une copie du dépôt sur un serveur : GitHub, GitLab (ou Bitbucket)
push / pull envoyer vos commits vers le distant / récupérer les commits des autres
clone télécharger un dépôt entier (avec son historique)
branche une ligne de travail parallèle, fusionnée plus tard

Git is not a backup of your data. It is made for text files (scripts, Rmd, Quarto, README, small CSV). Large files (rasters, photos, big Excel files) and personal data (names and phone numbers of interviewed households!) do not belong in a repository — especially a public one.

Git n’est pas une sauvegarde de vos données. Il est fait pour les fichiers texte (scripts, Rmd, Quarto, README, petits CSV). Les gros fichiers (rasters, photos, gros fichiers Excel) et les données personnelles (noms et téléphones des ménages enquêtés !) n’ont pas leur place dans un dépôt — surtout public.

The daily cycle: change, add, commitLe cycle quotidien : modifier, indexer, valider

The commands below are really run on this page (in a temporary folder). In RStudio you do the same with the Git pane: tick Staged, click Commit, write the message.

Les commandes ci-dessous sont réellement exécutées sur cette page (dans un dossier temporaire). Dans RStudio, vous faites la même chose avec le panneau Git : cochez Staged, cliquez sur Commit, écrivez le message.

cd "$DEMO"
git init -q -b main                       # 1. turn the folder into a repository (once)
mkdir -p R data/raw
echo 'reef <- read.csv("data/raw/reef_monitoring.csv")' > R/01_import.R
echo '# Reef monitoring' > README.md
git status --short                        # ?? = new files, not followed yet
?? R/
?? README.md
cd "$DEMO"
git add README.md R/01_import.R           # 2. stage: choose what goes in the commit
git commit -q -m "Start the project: README and import script"   # 3. commit with a message
git log --oneline                         # the history: one line per commit
246537b Start the project: README and import script

Now we change a file. git diff shows exactly what changed (- removed, + added) before we commit:

Modifions maintenant un fichier. git diff montre exactement ce qui a changé (- supprimé, + ajouté) avant de valider :

Good commit messages say why in a short sentence, in the imperative: “Lower the bleaching threshold to 20 %”, “Fix the site names of Tanjona”. Bad: “update”, “changes”, “final”. Commit often: one commit = one logical change.

Les bons messages de commit disent pourquoi en une courte phrase, à l’impératif : « Lower the bleaching threshold to 20 % », « Corrige les noms de sites de Tanjona ». Mauvais : « update », « modifs », « final ». Validez souvent : un commit = une modification logique.

To go back to an old version of one file: git restore --source=8c390f6 R/03_bleaching.R, then commit. Nothing is ever lost: the newer version is still in the history. In RStudio: Git pane → History (clock icon) lets you browse every commit and every file.

What Git must ignoreCe que Git doit ignorer

The file .gitignore lists the files Git never follows. A good start for an R project with renv:

Le fichier .gitignore liste les fichiers que Git ne suit jamais. Un bon début pour un projet R avec renv :

# R and RStudio

usethis::use_git_ignore(c("outputs/", "*.tif")) adds lines from R. Ignoring a file after it was committed is not enough: also run git rm --cached file to stop following it (it stays on your disk).

usethis::use_git_ignore(c("outputs/", "*.tif")) ajoute des lignes depuis R. Ignorer un fichier après l’avoir validé ne suffit pas : lancez aussi git rm --cached fichier pour qu’il ne soit plus suivi (il reste sur votre disque).

GitHub or GitLab: your project onlineGitHub ou GitLab : votre projet en ligne

GitHub (github.com) and GitLab (gitlab.com, or a server of your institution) are both free for public and private repositories. They work the same way for what we do here; the main difference is the vocabulary (GitHub pull request = GitLab merge request) and the publishing service (Session A9).

1. Create the empty repository online (New repository / New project), without README (your project already has one).

2. Prove who you are. Two methods:

GitHub (github.com) et GitLab (gitlab.com, ou un serveur de votre institution) sont tous deux gratuits pour les dépôts publics et privés. Ils fonctionnent de la même façon pour ce que nous faisons ici ; la principale différence est le vocabulaire (GitHub pull request = GitLab merge request) et le service de publication (séance A9).

1. Créez le dépôt vide en ligne (New repository / New project), sans README (votre projet en a déjà un).

2. Prouvez qui vous êtes. Deux méthodes :

HTTPS + personal token (easiest)HTTPS + jeton personnel (le plus simple)

usethis::create_github_token()   # opens GitHub: create a token, copy it
gitcreds::gitcreds_set()         # paste it: stored safely
# GitLab: Preferences -> Access tokens (scopes
# read_repository + write_repository), then the same

SSH key (no token to renew)Clé SSH (pas de jeton à renouveler)

ssh-keygen -t ed25519 -C "you@example.org"   # Enter x3
cat ~/.ssh/id_ed25519.pub   # copy this PUBLIC key into
# GitHub: Settings -> SSH and GPG keys -> New SSH key
# GitLab: Preferences -> SSH Keys
ssh -T git@github.com       # test: "Hi <name>! ..."

3. Connect and push (in the Terminal of your project):

3. Reliez et poussez (dans le Terminal de votre projet) :

git remote add origin git@github.com:your-account/reef-monitoring.git      # SSH
# or: https://github.com/your-account/reef-monitoring.git                  # HTTPS
# GitLab: git@gitlab.com:your-account/reef-monitoring.git
git push -u origin main        # first time; afterwards: git push

From R, usethis::use_git() then usethis::use_github() do steps 1 and 3 for GitHub in one go (with a token).

Depuis R, usethis::use_git() puis usethis::use_github() font les étapes 1 et 3 pour GitHub d’un coup (avec un jeton).

Two accounts on one computer (SSH)Deux comptes sur un même ordinateur (SSH)

With a personal and a work account, give each its own key and an alias in ~/.ssh/config. The alias then replaces github.com in the address of the remote — and it must be exactly the alias written in the config file, or the push fails with Could not resolve hostname.

Avec un compte personnel et un compte professionnel, donnez à chacun sa propre clé et un alias dans ~/.ssh/config. L’alias remplace alors github.com dans l’adresse du dépôt distant — et il doit être exactement l’alias écrit dans le fichier config, sinon le push échoue avec Could not resolve hostname.

# ~/.ssh/config
Host github-work
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_work
Host github-perso
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_perso

# test each alias, then use it in the remote address:
ssh -T git@github-work
git remote set-url origin git@github-work:organisation/reef-monitoring.git
git remote -v                       # check which address is used

Working with others: pull before you pushTravailler à plusieurs : pull avant push

  1. Pull (blue arrow in RStudio) before starting to work: you get your colleagues’ commits.
  2. Work, commit.
  3. Pull again, then push (green arrow). If Git refuses the push (rejected — fetch first), somebody pushed in the meantime: pull, then push.

To start from somebody else’s project: git clone <address> or, in RStudio, File → New Project → Version Control → Git.

  1. Pull (flèche bleue dans RStudio) avant de commencer à travailler : vous récupérez les commits de vos collègues.
  2. Travaillez, validez.
  3. Pull à nouveau, puis push (flèche verte). Si Git refuse le push (rejected — fetch first), quelqu’un a poussé entre-temps : pull, puis push.

Pour partir du projet de quelqu’un d’autre : git clone <adresse> ou, dans RStudio, File → New Project → Version Control → Git.

Branches and conflictsBranches et conflits

A branch lets you try something (a new indicator, a new figure) without disturbing the main version. If it works, you merge it; if not, you delete it. Here Hery changes the threshold on a branch while Fara changes the same line on main:

Une branche permet d’essayer quelque chose (un nouvel indicateur, une nouvelle figure) sans perturber la version principale. Si ça marche, on la fusionne (merge) ; sinon on la supprime. Ici Hery change le seuil sur une branche pendant que Fara change la même ligne sur main :

cd "$DEMO"
echo 'threshold <- 30' > R/02_indicator.R && git add . && git commit -q -m "Add the bleaching indicator"
git switch -q -c hery-threshold                 # new branch, and go on it
echo 'threshold <- 20' > R/02_indicator.R && git commit -q -am "Threshold 20 % (managers' request)"
git switch -q main                              # back on main
echo 'threshold <- 25' > R/02_indicator.R && git commit -q -am "Threshold 25 % (literature)"
git merge hery-threshold || true                # same line changed on both sides -> conflict
Auto-merging R/02_indicator.R
CONFLICT (content): Merge conflict in R/02_indicator.R
Automatic merge failed; fix conflicts and then commit the result.
cd "$DEMO"
cat R/02_indicator.R
<<<<<<< HEAD
threshold <- 25
=======
threshold <- 20
>>>>>>> hery-threshold

Git cannot choose between 25 and 20: it writes both versions between markers. You decide (talk to Hery!), edit the file to keep the right line and delete the markers, then add and commit:

Git ne peut pas choisir entre 25 et 20 : il écrit les deux versions entre des marqueurs. C’est vous qui décidez (parlez avec Hery !), modifiez le fichier pour garder la bonne ligne et supprimez les marqueurs, puis indexez et validez :

cd "$DEMO"
echo 'threshold <- 20   # agreed with the MPA managers, 2025-06-04' > R/02_indicator.R
git add R/02_indicator.R && git commit -q -m "Merge hery-threshold: keep 20 %"
git log --oneline --graph
*   fde48cf Merge hery-threshold: keep 20 %
|\  
| * c862be0 Threshold 20 % (managers' request)
* | b73c1f8 Threshold 25 % (literature)
|/  
* 0264722 Add the bleaching indicator
* 90ecbee Import the sites table
* 246537b Start the project: README and import script
