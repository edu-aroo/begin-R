A2 · Git and GitHub / GitLab with RStudioA2 · Git et GitHub / GitLab avec RStudio

~3.5 h

By the end of this session you will be able to

  • explain what Git does (the history of your project) and what GitHub and GitLab add (a copy online, to share and to keep safe);
  • install Git on Windows, connect it to RStudio and configure it once (the only time you use the Terminal);
  • create an account and a repository on GitHub or GitLab;
  • open the repository in RStudio as a version-controlled R project;
  • commit, push and pull with the buttons of RStudio — and know when to do each;
  • read the history, keep files out of Git, and solve a simple conflict.

À la fin de cette séance vous saurez

  • expliquer ce que fait Git (l’historique de votre projet) et ce qu’ajoutent GitHub et GitLab (une copie en ligne, pour partager et garder en sécurité) ;
  • installer Git sous Windows, le relier à RStudio et le configurer une fois (la seule fois où vous utilisez le Terminal) ;
  • créer un compte et un dépôt sur GitHub ou GitLab ;
  • ouvrir le dépôt dans RStudio comme projet R sous contrôle de version ;
  • valider (commit), pousser (push) et récupérer (pull) avec les boutons de RStudio — et savoir quand faire chacun ;
  • lire l’historique, garder des fichiers hors de Git, et résoudre un conflit simple.

Data of this session (simulated). You will put your own reef-monitoring project (Sessions A0–A1) under version control. To practise reading a history, reef_project_git.zip contains the same kind of project as prepared by the NGO with its Git history: six commits made in May 2025 by the two analysts, Fara and Hery (import, cleaning, a bleaching indicator whose threshold was changed after a meeting with the MPA managers, figures). Type: an R project plus the hidden .git folder that stores every saved version.

Pour vous entraîner à lire un historique, reef_project_git.zip contient le même type de projet préparé par l’ONG avec son historique Git : six commits faits en mai 2025 par les deux analystes, Fara et Hery (import, nettoyage, un indicateur de blanchissement dont le seuil a été changé après une réunion avec les gestionnaires des AMP, figures). Git, GitHub and GitLab in a nutshellGit, GitHub et GitLab en bref

  • Git is a program on your computer. In a project folder, it records snapshots of your files (commits), each with a date, an author and a message saying why. You can see what changed, who changed it, and go back. No more analysis_v3_FINAL.R.
  • GitHub (github.com) and GitLab (gitlab.com) are websites that keep a copy of your project online (a remote repository). They are a backup, a way to share with colleagues, and a place to publish (Session A9). Both are free; you need only one. GitHub is the most used; GitLab is common in some institutions and allows free websites from private projects.
  • RStudio has a Git pane with buttons for everything you need every day: you do not need to type Git commands.

pull get the commits made by others (or by you on another computer) blue arrow Pull
clone download a repository from GitHub / GitLab, with its history New Project → Version Control
  • Git est un programme sur votre ordinateur. Dans un dossier de projet, il enregistre des instantanés de vos fichiers (commits), chacun avec une date, un auteur et un message qui dit pourquoi. Vous voyez ce qui a changé, qui l’a changé, et pouvez revenir en arrière. Fini les analyse_v3_FINAL.R.
  • GitHub (github.com) et GitLab (gitlab.com) sont des sites web qui gardent une copie de votre projet en ligne (un dépôt distant). C’est une sauvegarde, un moyen de partager avec des collègues, et un lieu de publication (séance A9). Les deux sont gratuits ; un seul suffit. GitHub est le plus utilisé ; GitLab est courant dans certaines institutions et permet des sites gratuits depuis des projets privés.
  • RStudio a un panneau Git avec des boutons pour tout ce dont vous avez besoin chaque jour : inutile de taper des commandes Git.

Git is made for text files (scripts .R, reports .Rmd/.qmd, README.md, small CSV files). Do not put in a repository: large files (rasters, photos, big Excel files), files rebuilt by your scripts (outputs/), and above all personal data (names, phone numbers and GPS positions of interviewed people). We will exclude them with .gitignore.

Git est fait pour les fichiers texte (scripts .R, rapports .Rmd/.qmd, README.md, petits CSV). Ne mettez pas dans un dépôt : les gros fichiers (rasters, photos, gros fichiers Excel), les fichiers reconstruits par vos scripts (outputs/), et surtout les données personnelles (noms, téléphones et positions GPS des personnes enquêtées). Nous les exclurons avec .gitignore.

Step 1 — Install Git for WindowsÉtape 1 — Installer Git pour Windows

  1. Download Git for Windows from https://git-scm.com/download/win (the 64-bit Git for Windows Setup) and run it.
  2. Keep the default options, except on these screens:
    • Choosing the default editor used by Git: choose Use Notepad as Git’s default editor (simpler than Vim);
    • Adjusting the name of the initial branch in new repositories: choose Override the default branch name for new repositories and keep main;
    • Adjusting your PATH environment: keep Git from the command line and also from 3rd-party software (RStudio is the “3rd-party software”);
    • Choose a credential helper: keep Git Credential Manager — it will handle your GitHub / GitLab login (Step 8).
  3. Close and reopen RStudio after the installation, so that it finds Git.

Mac: open the Terminal app and type git --version; accept the installation of the “command line developer tools”. Linux: sudo apt install git.

  1. Téléchargez Git for Windows sur https://git-scm.com/download/win (le 64-bit Git for Windows Setup) et lancez-le.
  2. Gardez les options par défaut, sauf sur ces écrans :
    • Choosing the default editor used by Git : choisissez Use Notepad as Git’s default editor (plus simple que Vim) ;

Step 2 — Connect Git to RStudioÉtape 2 — Relier Git à RStudio

In RStudio, Tools → Global Options… → Git/SVN:

  • Enable version control interface for RStudio projects must be ticked: it shows the Git pane in projects that use Git.
  • Git executable is the path to the program git.exe, normally C:/Program Files/Git/bin/git.exe. If it is empty, click Browse… and select that file, click OK, and restart RStudio.

While you are in Global Options, open Terminal and set New terminals open with: Git Bash (a terminal that understands Git commands on Windows). Click OK.

Dans RStudio, Tools → Global Options… → Git/SVN :

  • Enable version control interface for RStudio projects doit être coché : cela affiche le panneau Git dans les projets qui utilisent Git.
  • Git executable est le chemin du programme git.exe, normalement C:/Program Files/Git/bin/git.exe. S’il est vide, cliquez sur Browse… et sélectionnez ce fichier, cliquez OK, et redémarrez RStudio.

Tant que vous êtes dans Global Options, ouvrez Terminal et réglez New terminals open with: Git Bash (un terminal qui comprend les commandes Git sous Windows). Cliquez OK.

Step 3 — Tell Git who you are (once per computer)Étape 3 — Dire à Git qui vous êtes (une fois par ordinateur)

Each commit is signed with a name and an e-mail. You set them once on each computer. This is the only time in this lesson that we type commands: in RStudio, Tools → Terminal → New Terminal (Alt + Shift + R) opens a terminal at the bottom, next to the Console. Type each line and press Enter:

Chaque commit est signé d’un nom et d’un e-mail. Vous les réglez une fois sur chaque ordinateur. C’est la seule fois dans cette leçon que nous tapons des commandes : dans RStudio, Tools → Terminal → New Terminal (Alt + Maj + R) ouvre un terminal en bas, à côté de la Console. Tapez chaque ligne et appuyez sur Entrée :

git config --global user.name "Fara Rasoa"
git config --global user.email "fara@example.org"
git config --global init.defaultBranch main
git config --global --list
Part of the command What it means
git config the Git command that reads and writes Git settings
--global an option: the setting is for every project of this Windows user (without it, only for the current project)
user.name "Fara Rasoa" the name written in your commits — your real name, between quotes because it has a space
user.email "…" the e-mail written in your commits: use the one of your GitHub / GitLab account, so the website links the commits to you
init.defaultBranch main the name of the main branch of new repositories (main, like GitHub and GitLab)
--list prints all the settings, to check them

Without the Terminal, the package usethis does the same from the Console:

Sans le Terminal, le package usethis fait la même chose depuis la Console :

usethis::use_git_config() writes Git settings; each argument has the name of the Git setting with a dot (user.name =, user.email =) and takes a text value. pkg::function() calls a function of a package without library() (Beginner, Session 8).

usethis::use_git_config() écrit des réglages Git ; chaque argument porte le nom du réglage Git avec un point (user.name =, user.email =) et attend une valeur texte. pkg::fonction() appelle une fonction d’un package sans library() (débutant, séance 8).

Step 4 — Create an accountÉtape 4 — Créer un compte

GitHub — go to https://github.com → Sign up:

  1. enter your e-mail (the same as in Step 3), a password and a username — it appears in the address of your projects (github.com/username/…), so choose something short and professional, e.g. fara-rasoa;
  2. confirm with the code sent by e-mail;
  3. set up two-factor authentication when GitHub asks (it is required for accounts that push code): install an authenticator app on your phone (e.g. Microsoft Authenticator), scan the QR code, and save the recovery codes in a safe place.

GitLab — go to https://gitlab.com → Register now: first and last name, username, e-mail, password, then confirm your e-mail. GitLab may ask you to confirm your identity (for example with a phone number) before you can use some features; follow its instructions. You can also activate two-factor authentication in Preferences → Account.

  3. activez l’authentification à deux facteurs quand GitHub le demande (elle est obligatoire pour les comptes qui envoient du code) : installez une application d’authentification sur votre téléphone (ex. Microsoft Authenticator), scannez le QR code, et gardez les codes de récupération en lieu sûr.

GitLab — allez sur https://gitlab.com → Register now : prénom et nom, nom d’utilisateur, e-mail, mot de passe, puis confirmez votre e-mail. Step 7 — CommitÉtape 7 — Valider (commit)

  1. In the Git pane, click Commit: the Review Changes window opens.
  2. Tick Staged for the files that belong to the same change (e.g. the cleaning script and the README that explains it). Click a file to see its diff: green lines added, red lines removed.
  3. Write a commit message: one short sentence that says why, e.g. “Remove duplicated transects of 2026”. Bad messages: “update”, “changes”, “final”.
  4. Click Commit. A small window confirms it (“1 file changed…”): close it.

The commit is now saved on your computer only. Nothing is online yet: that is the Push (Step 8).

When to commit? After each logical step that works: a script that runs, a figure finished, a section of a report written, a bug fixed. Commit often — several times per work session — with small commits: they are easier to understand and to undo. Do not commit a script that does not run, and do not wait until the end of the week.

  1. Dans le panneau Git, cliquez sur Commit : la fenêtre Review Changes s’ouvre.
  2. Cochez Staged pour les fichiers qui font partie de la même modification (ex. le script de nettoyage et le README qui l’explique). Cliquez sur un fichier pour voir son diff : lignes vertes ajoutées, lignes rouges supprimées.
  3. Écrivez un message de commit : une courte phrase qui dit pourquoi, ex. « Supprime les transects en double de 2026 ». Mauvais messages : « update », « modifs », « final ».
  4. Cliquez sur Commit. Une petite fenêtre le confirme (« 1 file changed… ») : fermez-la.

Le commit est maintenant enregistré sur votre ordinateur seulement. Rien n’est encore en ligne : c’est le Push (étape 8).

Quand valider ? Après chaque étape logique qui marche : un script qui tourne, une figure terminée, une section de rapport écrite, une erreur corrigée. Validez souvent — plusieurs fois par séance de travail — avec de petits commits : ils sont plus faciles à comprendre et à annuler. Ne validez pas un script qui ne tourne pas, et n’attendez pas la fin de la semaine.

Step 8 — Push and pullÉtape 8 — Pousser (push) et récupérer (pull)

  • Push (green arrow ⬆, in the Git pane or the Review Changes window) sends your commits to GitHub / GitLab. Refresh the page of your repository in the browser: your files and messages are there.
  • Pull (blue arrow ⬇) downloads the commits that are online and not yet on your computer: those of a colleague, or yours made on another computer.

When?

  • Pull when you start working (open the project → Pull), so you start from the latest version.
  • Push at least at the end of each work session — your work is then backed up online — and whenever a colleague needs your changes.
  • Pull just before you push. If RStudio says the push was rejected (“Updates were rejected… fetch first”), somebody pushed in the meantime: click Pull, then Push again.
  • Push (flèche verte ⬆, dans le panneau Git ou la fenêtre Review Changes) envoie vos commits vers GitHub / GitLab. Actualisez la page de votre dépôt dans le navigateur : vos fichiers et messages y sont.
  • Pull (flèche bleue ⬇) télécharge les commits qui sont en ligne et pas encore sur votre ordinateur : ceux d’un collègue, ou les vôtres faits sur un autre ordinateur.

Quand ?

  • Pull quand vous commencez à travailler (ouvrir le projet → Pull), pour partir de la dernière version.
  • Push au moins à la fin de chaque séance de travail — votre travail est alors sauvegardé en ligne — et dès qu’un collègue a besoin de vos modifications.
  • Pull juste avant de pousser. Si RStudio dit que le push a été rejeté (« Updates were rejected… fetch first »), quelqu’un a poussé entre-temps : cliquez sur Pull, puis à nouveau sur Push.

The first push: signing inLe premier push : se connecter

GitHub and GitLab do not accept your account password from Git. On Windows, the first Push (or Pull of a private repository) opens a Git Credential Manager window: click Sign in with your browser, log in on the website, click Authorize. Windows then remembers it safely: you will not be asked again on this computer.

If that window does not appear, use a personal access token (a long password made only for Git):

GitHub et GitLab n’acceptent pas le mot de passe de votre compte depuis Git. Sous Windows, le premier Push (ou Pull d’un dépôt privé) ouvre une fenêtre Git Credential Manager : cliquez sur Sign in with your browser, connectez-vous sur le site, cliquez sur Authorize. Windows s’en souvient ensuite en sécurité : on ne vous le redemandera plus sur cet ordinateur.

Si cette fenêtre n’apparaît pas, utilisez un jeton d’accès personnel (personal access token : un long mot de passe fait uniquement pour Git) :

usethis::create_github_token()   # opens GitHub on the page to create a token: keep the proposed boxes, set an expiry date, copy the token
gitcreds::gitcreds_set()         # then paste the token when the Console asks for it; it is stored safely by Windows

create_github_token() needs no argument; it only opens the right web page with the right boxes ticked. gitcreds_set() asks for the token in the Console and stores it in the Windows credential store, where Git and usethis find it. GitLab: Preferences → Access tokens → Add new token, tick the scopes read_repository and write_repository, copy the token; at the first Push, choose the Token tab of the Credential Manager window (or type your username and paste the token as password). A token is like a password: never put it in a script or a commit.

create_github_token() n’a pas besoin d’argument ; elle ouvre seulement la bonne page web avec les bonnes cases cochées. gitcreds_set() demande le jeton dans la Console et le range dans le gestionnaire d’identifiants de Windows, où Git et usethis le trouvent.   1. Invitez votre collègue : GitHub → votre dépôt → Settings → Collaborators → Add people ; GitLab → Manage → Members → Invite members (rôle Developer). Elle clone le dépôt dans RStudio (étape 6).
  2. Chacun suit le cycle Pull → travail → Commit → Pull → Push. Si vous travaillez sur des fichiers différents, Git fusionne tout automatiquement.
  3. Un conflit arrive quand vous avez tous deux modifié les mêmes lignes du même fichier. Après votre Pull, RStudio affiche le fichier avec le statut U. Ouvrez-le : Git a écrit les deux versions entre des marqueurs :

bleach_threshold <- 25   # your version
=======
bleach_threshold <- 20   # the version of your colleague
>>>>>>> 4a5c8d0
  1. Decide together which is right, edit the file to keep only the right line(s), delete the three marker lines, save.
  2. In the Git pane: tick Staged for the file, Commit (RStudio proposes a “Merge…” message), Push.

Conflicts are rare if you pull often and commit small changes.

Going further: a branch (Git pane → “New Branch” button) lets you try something without touching the main version; you then merge it on the website with a Pull request (GitHub) or Merge request (GitLab). Useful in teams, not needed for your own projects.

  1. Décidez ensemble laquelle est juste, modifiez le fichier pour ne garder que la ou les bonnes lignes, supprimez les trois lignes de marqueurs, enregistrez.
